# Fixtures

A fixture is a **regression set** for the skills in this repo. Without one, every edit to a `SKILL.md` is settled by opinion — which is exactly how sediment survives a pruning pass.

## Working file vs fixture

Two artifacts, same encounters, opposite lifecycles. The repo used to have one word for both.

| | Working file | Fixture |
| --- | --- | --- |
| Lives in | `scratch/` | `fixtures/` |
| Committed | never | always |
| Carries | everything needed for Medatrax entry | ages and clinical findings only |
| Job | doing the work | proving the skill still does the work |

A fixture is **derived from** a working file, never a copy of one. Two things are removed on the way across:

- **The visit date.** Dates finer than a year are the identifier that matters here.
- **The site name.** Date plus site plus age narrows the population sharply in a small county — **and the line above has already removed the date, so what a fixture can actually leak is site plus age.** [#50](https://github.com/mshamblin5150-code/clinical-skills/issues/50) ruled that too little to justify a scanner layer and more than enough to keep removing. **The removal binds; only the reason is weaker than this sentence sounds.**

Names are already `[PT]` under standing rule 1. Ages and findings stay, because they are what the assertions test.

**Compute the age before removing either.** Nearly half this clinician's encounters give a date of birth and no age. Removing the visit date and redacting the date of birth in the same pass leaves a case whose age cannot be recovered by anyone — including the fixture, which needs it. Derive first, then strip both. A fixture that has lost its age is testing the missing-age rule whether it meant to or not.

**A fixture derived from a skill's *output* inherits that skill's whole context, not its input's.** Everything above assumes the source is a working file, where the two removals are the whole story: what crosses is what the working file carried, minus what was struck. `filled-anchor` is the first set whose inputs are a skill's output rather than shorthand, and the assumption failed on it immediately. `clinical-note` reads the account profile in `scratch/` to decide a payer, so most of its twelve notes named a practicum site — generated from shorthand that named none. **That set's own README had argued in writing that this could not happen**, and it is the argument to distrust: a note cannot reintroduce what its *prompt* did not carry, and its prompt is not its context.

**So when the source is generated, the list above is a floor rather than a list.** Read what the generating skill reads, and check the output against *that* — never against the input, which is precisely the artifact that cannot tell you. Nothing enforces this. `phi_scan` knows patient names, corpus dates and PHI shapes, and an account profile is none of the three.

**[#50](https://github.com/mshamblin5150-code/clinical-skills/issues/50) ruled the site names themselves acceptable and built no scanner layer**, on the site bullet above losing its date term, on the exposure being portal mechanics — which placements the clinician works, a fact about him rather than about any patient — and on the repo being private. **The removal rule is untouched**: [standing rule 1](../AGENTS.md) still defines a fixture as one with the visit date and site removed, and *ruled not worth tooling* is not *ruled not worth doing*.

**What the ruling actually preserved is this section rather than the site names**, and the difference is the whole reason it is written here instead of in that set's own file. A site list would have caught two strings in one set. The next set built from generated output inherits a **different** file — whichever one its generator happens to read — and the thing to refuse is reasoning from what the input carried. **How many notes leaked what, and in whose wording, is counted once** in [filled-anchor/notes/README.md](filled-anchor/notes/README.md) with the command that recomputes it, and is deliberately not restated here: #50's own first draft restated a count and a quoted phrase into three files and got both wrong.

## What an assertion is

A claim, in the clinician's own words, about what a correct run must contain — checked against the output text.

It is deliberately **not** a diff of the note prose: prose varies legitimately from run to run, and a bar that trips on style gets ignored within three runs.

It is also deliberately **not** the drift-matrix verdicts from `clinical-note` step 7. Those are the skill grading itself — a run that misses snuff box tenderness is precisely the run that also emits `row 2: PASS`. See [docs/adr/0001](../docs/adr/0001-fixture-asserts-on-named-findings.md).

## The pass bar

**DRIFT assertions are binary.** All of them, every run, no exceptions. Each one is a documented abnormal that reached the Objective and stopped there — the defect class the skill exists to catch. One miss fails the run.

**FILLED assertions are binary.** Same bar as DRIFT, different subject: what the skill does with a value the shorthand never supplied. DRIFT asks whether a *given* abnormal survived to the Assessment; FILLED asks whether a *generated* one was produced at all, was plausible for that patient, and then survived the same way. They are separate classes because they ask different questions of the same run, and a set can hold rows of one and none of the other. A set with no reference read may hold no DRIFT row. A set whose inputs supply every value the note needs holds no FILLED row.

**FILLED asks one more thing, and it runs the other way.** Everything above is additive — what work the generated value made the note do. [Issue #27](https://github.com/mshamblin5150-code/clinical-skills/issues/27) was the subtractive case: a generated value making the note do *less*, by becoming the reason a workup was withheld. `clinical-note` rules that a filled value may raise an obligation and never discharge one, and a row holding a set to that is a FILLED row for the same reason the others are — its subject is a value the shorthand never supplied. day-b's B9 is the worked example. **Note which side of a set's reference read this lands on:** a submitted note labels no filled values, so this is the one FILLED question a reference can never answer, however carefully it is read.

**And FILLED's subject is a generated *item*, not only a generated *value*.** [Issue #47](https://github.com/mshamblin5150-code/clinical-skills/issues/47) is the case: a note that writes a Plan item into `FILLED·proposed` and never writes it into the Plan has dropped something it generated, and the row that counts them — day-b's B16, peds-bp's P8 — is a FILLED row on the same test as every other. **This file already read it that way once and did not act on it**: day-b's D6 records that what its row checks for is *"a **generated** order, which is FILLED's subject rather than DRIFT's under fixtures/README"*, and then keeps the row in DRIFT for reasons about *given* content. What changes now is only that a set may host such a row directly. **DRIFT is untouched**, and so is GIVEN: an order the *shorthand* wrote is still GIVEN's, and one this skill contributed is FILLED's, which is the same provenance line the two classes already run on.

**But FILLED is no longer the vitals class**, and the difference is worth stating because it changes which sets can host one. What admits a row is that the value was generated and the skill licensed generating it; `clinical-note` states that license as a test — a box demands a value and the shorthand constrains none — and names three members. day-b's B1 through B4 are the vital and body-measurement half, and only its nine vital-less cases reach them. B5 through B8 are the OLDCARTS half, and they reach all twelve: shorthand never supplies eight OLDCARTS elements, so **that half of the class fires on every input there is.** A set with complete vitals throughout, like day-a, is no longer a set with no FILLED row to write. B9 belongs to neither half — it is the subtractive question above, asked of all three members at once, and it reaches whichever cases had a value generated for them.

**ANCHOR and CODE assertions are binary, and they belong to `icd10-cpt` rather than to `clinical-note`.** DRIFT asks what a note did with a finding it was given; FILLED asks what it did with one it generated under license. Neither question means anything for a skill that generates nothing and writes no prose — which is why `filled-anchor` brings two classes rather than reusing these. ANCHOR asks whether a proposed code rests on a number the encounter actually recorded — the rule [#10](https://github.com/mshamblin5150-code/clinical-skills/issues/10) added, whose whole failure mode is that it is invisible when it fails. CODE asks whether a proposed code exists, carries its official descriptor, and can be submitted.

**CODE is the only *class* in this repo a machine decides**, and since [#67](https://github.com/mshamblin5150-code/clinical-skills/issues/67) it is no longer the only *row*. `python tools/icd10_lookup.py` answers all three of CODE's questions against `reference/icd10cm-2026.sqlite`, so no reader is involved and two readers cannot disagree; **day-b's B13 is settled the same way** by `tools/filled_vitals_census.py`, which exits non-zero when two notes share a filled body. Every other row here, binary ones included, needs someone to read the output and rule.

**A machine-decided row is worth more than the convenience**, and it is worth saying what it actually buys: not speed, but that a **second grader gets the same answer**. Everything else in this file rests on the separation between the pass that produced a run and the pass that scored it, and that separation is only as good as two readers agreeing. Where a row can be reduced to a command, reduce it — and where it cannot, say what the reader is bounded by, which is what every binary row here already does.

**CODING assertions are binary**, and they belong to `clinical-note` — the codes a **note** carries, as against the codes a worksheet proposes. DRIFT asks whether a given abnormal survived, FILLED asks what happened to a value nobody supplied, and CODING asks whether the codes attached to what survived say what the encounter can support. It is a separate class because a set can hold one and not the others: its rows turn on a code string being present or absent in the note text, which needs neither a reference read nor a vital-less input.

**CODING is not CODE, and the names sit close enough to be worth separating.** CODE asks whether a code number is real, correctly described and submittable, and `icd10_lookup.py` answers it. CODING asks whether the note attached a code that claims more than the encounter established, and **no lookup can decide that** — `U07.1` is a real, billable, correctly described code, which is precisely what makes it wrong on a COVID nobody swabbed. A set passing every CODE row can fail every CODING row with codes that all exist.

**GIVEN assertions are binary, and they belong to `clinical-note`.** The three classes above all ask what a note *did* with something — a finding it was given, a value it generated, a diagnosis it coded. GIVEN asks the prior question: **is the given still there.** A test the plan line ordered, a referral the clinician made, a drug he prescribed, a stated allergen, a transcribed number — the tier system's first sentence is that these pass through unchanged, and a GIVEN row is that sentence made checkable on one of them.

**It is a separate class because DRIFT cannot hold it without changing what `DRIFT n/m` means.** DRIFT is a documented **abnormal** that reached the Objective and stopped; an order is not an abnormal and not a finding, and widening the definition would retroactively redate two sets' recorded scores. **Appending a class costs a section; editing one costs every number already reported under it.**

**Its failure is not a silence, which is what separates it from every class above.** A drifted finding is missing from the note. A dropped order can be *replaced* — by the note's own decision not to have ordered it, written out as clinical reasoning — and then the note is not incomplete, it is **wrong about the encounter**, under the clinician's name. A GIVEN row therefore says both things: the given must be present, and no sentence may stand where it was. day-b's G1 is the worked example, from [#66](https://github.com/mshamblin5150-code/clinical-skills/issues/66).

**Two existing rows have GIVEN's subject and are staying where they are.** day-b's B4 — *every given vital appears in the note unchanged* — and B7, the same for a given severity, are FILLED rows because they were written as controls on the filled-value license. Renumbering them into this class would redirect every citation to them, and **append, never insert** applies to rows across a reorganization exactly as it does to a drift matrix. What they show is that the question was being asked before there was a class for it, and only ever about values.

**REPORTED assertions are counted, not enforced.** Differential depth, screening content, education phrasing. They move with the model and the wording; tracking the count catches slow erosion without failing a run over style.

**A row's subject is usually one case and it does not have to be, and day-b's B13 is the first that is not.** Every other row in this repo names a case list and is checked note by note. B13's `Cases` column reads **the set**, because its subject is two notes agreeing with each other: *no two of the nine filled cases carry an identical height-and-weight pair*. **No per-case row can hold that**, however it is worded — read case 1 alone and `5'10" / 190 lb` is an ordinary patient, and it stays one until case 5 turns up with the same body at an age thirty-two years different.

**It is still binary and it is still checked against the output text**, so nothing about the bar changes. What changes is the unit: a miss names two cases rather than one, and a set with one filled case cannot host such a row at all. **Say which shape a row is by what its `Cases` column holds**, and reserve the set shape for claims that genuinely need it — a row that could be written per case and was written per set has made itself harder to score for nothing.

**The defect this shape exists for is invisible by construction**, which is the argument for tolerating a second row shape at all. [Issue #67](https://github.com/mshamblin5150-code/clinical-skills/issues/67) is a run whose every note is individually defensible and whose set describes one patient nine times. Twelve independent generating passes were needed to see it, and the separation this file already insists on — the pass that grades did not write — is what put twelve outputs in front of one reader.

**Not every counted row is counted for that reason, and the distinction matters when one is promoted.** [Issue #29](https://github.com/mshamblin5150-code/clinical-skills/issues/29) added day-b's R2 through R4 and rewrote day-b's R1 and day-a's R14 — **five rows, one ruling, two sets.** None of the five moves with wording: they resolve to whether a template slot carries a value, whether that value is a hedge, whether the block declares it, whether a withheld dependency is named, and whether an asserted detail is grounded in the shorthand. They are counted because both sets are already behind on runs, and because enforcing one set's half while the other waits would have the two files hold the same rule to different standards. **A row counted for want of a run is promotable and a row counted for turning on phrasing is not**, so a set that holds both says which each is. R1 and R14 predate #29 and are counted for the second reason no longer — their rewrites removed the phrasing they used to turn on.

**A counted row can have a binary class's subject, and day-b's R2 through R4 do.** Their subject is a filled value, which is FILLED's by the definition above — but FILLED is binary in that same definition, so there is no counted `B` row to be. They are R-numbered, the prefix follows the bar rather than the subject, and day-b's own file says why at length. **The consequence to know is that the class names no longer partition by subject alone**: a `REPORTED n/m` denominator may cover rows whose subject is FILLED's.

**CODING is binary and differential *depth* is not, which looks like a contradiction and is not.** How many entries a differential runs to moves with the model, so it is counted. Whether each of those entries carries a code does not move at all — it is two integers compared. The line is the one below: the subject can be soft while the claim about it stays hard.

**What makes a row enforceable is that it does not move with wording.** A row resolving to a value or its absence — is there a pressure in the FILLED block, is it below 130 over 80, does the finding appear in the Assessment — can be binary. A row turning on how well something is phrased cannot, and belongs in REPORTED however important it is.

**There is a third reason to count a row, and it is neither of the two above: the claim is hard and there is no bar to set.** day-b's R5 is the case. It reports three integers over a set — how many distinct heights and pressures the filled values take, and how many of those pressures are not normal — and a machine prints all three, so nothing about it moves with wording. **What is missing is a threshold.** The corpus says roughly half of this clinician's transcribed pressures are below 130/80; that is a direction, and turning it into a pass condition over nine samples means picking a number nobody has grounded. A run failing *no more than six of nine* would be failing an opinion.

**So the enforceable fragment gets written as a binary row and the rest is counted.** *Identical* needs no threshold, which is why day-b's B13 is binary and R5 is not. **This kind is not promotable and it is not waiting for anything** — unlike a row counted for want of a run, no future run makes a threshold appear. Promoting it would require a ruling from the clinician about what rate is wrong, which is a different thing from a run.

**And a counted row is still what found the defect.** #67 is a distribution nobody could have failed a run over, and it produced a skill rule, a drift row and two binary rows in this file. **A number that grades nothing is not a number that does nothing.**

## Running a set

1. Feed each case's input to the named skill, on the stated branch. For most sets that is the shorthand; for a set whose skill consumes a finished note it is the note and its tier block, and the set's own `Inputs` column says which.
2. Check the output text against that case's assertions.
3. Report every class the set defines — the binary ones must be full, and `REPORTED n/m` alongside. A set that defines no rows of a class omits its line rather than reporting `0/0`.
4. Any miss in a binary class names the case, the finding or the code, and where it landed instead. For a CODING miss that is the entry and the code it carried, or that it carried none.

Re-run after every `SKILL.md` edit. That is the entire point: a measurable delta instead of a judgment call.

**A first run graded by whoever wrote it is a baseline, not a pass.** The same objection that disqualified the drift-matrix verdicts in [ADR 0001](../docs/adr/0001-fixture-asserts-on-named-findings.md) applies to any run scored by the pass that produced it. Asserting against the output text rather than a self-report is what makes the score checkable at all — someone else can re-read the same text and disagree. Until someone does, the number's job is to give the next run something to differ from.

**So separate the two passes, and it is cheap enough that there is no excuse not to.** day-b and peds-bp were both run this way on 2026-08-11: subagents wrote the notes with the assertion files withheld, a fresh pass graded the output text against them, and the orchestrating pass re-derived every row from the output files having authored none of them. What it bought was immediate — **each set failed a row**, and in both cases the note's own drift matrix had reported that row as a pass, once citing Plan text the Plan did not contain. That is ADR 0001's argument happening rather than being made, twice in one sitting.

**day-b run 2 is the third instance and the most useful one, because the run passed.** Separated the same way on 2026-08-12 — twelve generating passes, five fresh grading passes split by class, and an orchestrating pass that authored no note — it cleared every binary row, **and a note's drift matrix was still wrong about a Plan**, on a row that passed anyway. The case and the quotation are in [day-b/assertions.md](day-b/assertions.md).

So the separation is not just for catching failures. **A self-report can be wrong in a run that passes**, where nothing else would ever prompt anyone to check it.

**day-b run 3 is the fourth instance and the sharpest, on two of the three rows it failed.** Separated the same way on 2026-08-12 — twelve generating passes, seven grading passes split by class, an orchestrating pass that authored no note — it failed three rows, and **three notes reported drift row 17 as a pass on the three cases that fail the two social rows**. One said *"twelve carry a value and none is a hedge"* while its own allergy line hedged six times. A fourth self-report claimed a Plan item that Plan does not contain, which is [#47](https://github.com/mshamblin5150-code/clinical-skills/issues/47) for the third consecutive run.

**The third failure is the opposite case and is worth separating.** No matrix claimed that row at all — the self-report simply does not reach it — so it is a **gap** in the self-report rather than a false statement by it. Both defeat a self-graded run, and only the first is the thing [ADR 0001](../docs/adr/0001-fixture-asserts-on-named-findings.md) is about.

**A run graded by itself would have scored this one clean either way.** Three reports wrong in the same direction, each on the row that would have caught it, and a fourth row nothing was looking at.

**Withhold the set's `shorthand/README.md` too, not just `assertions.md`.** Both inputs READMEs state what their set exists to test, and day-b's names two assertion rows outright. Three of the ten generation passes on that day read one — five of the seventeen cases — having reasoned that a file in the inputs directory was an input. All five were regenerated from scratch by passes that had not.

**Paste the input instead of pointing at it, and the reasoning has nowhere to go.** day-b run 2 gave each generating pass its shorthand inline and told it that `fixtures/` was closed for any purpose, naming this repo's own `AGENTS.md` link to this file as one not to follow. **Twelve of twelve reported opening nothing there, and nothing was regenerated** — against five of seventeen the run before. A path into the inputs directory is what makes the neighboring file look like an input; without one there is no directory to be curious about.

**That audit is a self-report, and it cannot be made anything better.** Each pass was asked afterwards to list every file it opened; three said yes, the rest said no, and the yeses are the only reason the regeneration happened. **Nothing in the output distinguishes a contaminated run from a clean one** — that is what makes the contamination worth avoiding, and it is also why no later check can catch it. ADR 0001 rejects a self-report as *evidence for a verdict*, which this is not: it is an admission against interest, and the correct response to one is to re-run rather than to trust it. **Withhold the file up front**, because the audit cannot be relied on to find what the prompt failed to prevent.

**`filled-anchor` is not among them, and it could not have been.** The defect above has no subject in it: `icd10-cpt` writes no Objective and generates no value, so there is nothing there to reach one and stop. What it can catch is the same value one skill later, which is the whole of why it exists — and on run 1 it caught nothing, because the run refused every filled anchor it was offered. **A pass on a set this young is a baseline, not a clean bill.**

**Its ANCHOR column was withdrawn for four days, and the reason is this section's own rule arriving at a fourth set.** [#46](https://github.com/mshamblin5150-code/clinical-skills/issues/46) reversed A1, A2 and A5 from *withhold the code* to *propose it marked*, so the refusal that earned run 1 its `5/5` failed all three rows. **The run did not change and was not wrong; the bar moved underneath it** — which is the #29 situation exactly, and takes the same remedy. **The column reads `5/5` again and it is not the same `5/5`**, which is the thing a withdrawn-then-refilled digit hides. Run 1 earned it by refusing every filled anchor it was offered; run 2 earned it by proposing all 29 of them marked, and by matching every mark to a step-4 listing. **Same digit, opposite behavior, and only the second one is what the rows ask for today.**

**Then [#56](https://github.com/mshamblin5150-code/clinical-skills/issues/56) moved the other two columns, and it is the first time a row in this repo has *split* rather than moved.** `icd10-cpt` permitted a bare `SPECIFICITY: complete` while `filled-anchor`'s R2 failed one, so a run could satisfy the skill in full and lose the row. #56 tightened the skill — `complete` carries its reason, and a code whose official descriptor says `unspecified` may not read `complete` at all — and then **took R2 apart along the line this section already draws**: the half that resolves to a string became **C5**, binary and enforced, and the half that turns on whether a reason is a real check or a stock phrase stayed in REPORTED. `CODE` read `4/5` because C5 was unscored, on the growing-denominator rule below, and `REPORTED` read `1/1` because R2's verdict was **withdrawn**, on the same rule ANCHOR's was. **Run 2 has since scored both, and both pass** — C5 with zero faults over 200 flags, and R2 on evidence run 1's format could not have produced: 24 codes carry a `complete` flag in more than one worksheet, and 61 of those 62 reasons are distinct. **Twelve passes that could not see each other's text did not converge on a sentence**, which is the strongest thing available to a row that turns on whether a reason was arrived at by looking. *Text* is the load-bearing word and it is narrower than the first draft's: several passes ran a counts-only scanner over the shared output directory, so a few saw aggregate totals covering worksheets they never opened. The run's own README lists which.

**A withdrawal that shrinks a denominator is the one to check**, and this one does not hide the miss: run 1's single bare `complete` was a *counted* miss in a class the set still passed, and under C5 the identical flag fails an enforced row outright. **It got stricter on its way out of REPORTED.**

**C5 is the third machine-decided row here**, on day-b's own counting — the CODE class is the first and B13 the second. **It is the second to arrive with a tool written for it**, not the first: `tools/filled_vitals_census.py` and B13 both came out of [#67](https://github.com/mshamblin5150-code/clinical-skills/issues/67) in one landing, and only C1 through C3 borrowed a tool — `icd10_lookup.py` — that already existed for the skill.

## A set has two halves

**Inputs** are whatever the set's skill consumes, committed under the set. For every `clinical-note` set that is the shorthand — extracted from the day-file scan, de-identified, under `shorthand/`. For `filled-anchor` it is finished notes with their tier blocks, under `notes/`, because that is what `icd10-cpt` takes.

**An input further down the pipeline is a skill's output, and that carries one obligation.** A set built on generated material must not read as endorsing it: the note is *real input*, not *correct input*, and a row quoting it is quoting an artifact rather than a source. **`filled-anchor` names the generating run's score in its own *Still unresolved*, and it is no longer the absence of one that has to be disclosed** — day-b has since run and *failed a FILLED row*, so these twelve notes are known-real, known-incomplete, and known-wrong in at least one place. That is a stronger reason to keep the obligation than "unscored" ever was.

**Reference** is what the clinician actually submitted to the portal. It is a **baseline to beat, not a target to match**, and the skill exists to do better than it consistently. A difference from the reference is therefore *better*, *worse*, or *neither* — and only *worse* is a regression.

**The reason it is a baseline is not the one this file used to give.** It said the submitted notes were *"written under time pressure at the end of a long shift."* **The reference reads falsified that**: day-b's twelve were typed 78 days after the shift and `peds-bp`'s five 52 days after. They were written from the day file, long after the room, and the day file is the only record of what was in it.

**Two things follow, and both were stated by the clinician on 2026-08-12.**

**The notes predate the corpus.** *"I put those assessments in before I started cataloging them as the corpus has, so if there is anything missing from the notes in Medatrax that is why."* The transcribed corpus these fixtures are built from is the **newest** layer — the day file came first, the portal note second, the catalog last. **A reference note is not a note written to this repo's standard and falling short; it is a note written before the standard existed.**

**And whether anything is missing from one is unknowable.** Asked directly: ***"and they could be, I don't know."*** Nobody can reconstruct what did not make the trip from paper to portal, and no re-read will produce it.

**So a finding absent from a reference is not evidence of a reasoning failure.** It may be one, and it may equally be a line that was never typed. **No row may rest on a reference being complete** — which is why the fourth verdict exists, why *worse* is the only regression, and why a `Reference did` cell records what the note contains rather than what the clinician knew. This is the same class of permanently-open question as the provenance of a filled vital, and it is answered the same way: word the row so it holds either way.

The reference has to be read, never inferred. Inferring it from the skill's own prior output produces a set that agrees with itself forever.
