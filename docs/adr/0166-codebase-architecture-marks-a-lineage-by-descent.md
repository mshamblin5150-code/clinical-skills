# `codebase-architecture` marks a lineage by descent

[#1047](https://github.com/mshamblin5150-code/clinical-skills/issues/1047) was found by the tracker
sweep out of [#873](https://github.com/mshamblin5150-code/clinical-skills/issues/873)'s grilling.
`CLAUDE.md` names `docs/agents/triage-labels.md` as the home of the complete label vocabulary, and
[ADR 0072](0072-blocked-is-one-kind-agnostic-gate-label-on-an-axis-orthogonal-to-the-roles-and-the-sweep-holds-its-invariant.md)
ruling 4 ruled that every label is documented there and none is deleted. One label had no row:
`codebase-architecture`, described on GitHub as *"Deepening opportunity found by an architecture
review; orthogonal to the triage role"*.

Grilled 2026-09-10 at `origin/main` `75861e0`. The session was brought forward to `6dde06c` before
this record was written. **Six questions were ruled by the clinician one at a time on that date**; the sixth widened ruling 2
after a trace of the label's carriers found a ticket a build had filed.
Nothing is built here; this is the record the build reads. Every count below is a dated measurement,
not a current property of the tracker.

## Measured before ruling

### The label postdates the ruling that should have documented it

`gh label list` gives `codebase-architecture` a creation time of `2026-09-03T00:01:42Z`, five days
after ADR 0072 ruled 2026-08-29 and on the day an architecture review's tickets were filed. Nothing
in the tree names the label. `git log --all -S codebase-architecture` returns no commit, and no tool,
workflow or document reads it.

### A per-ticket label audit cannot see a missing row

Sweep comments on #921, #874, #875, #836 and #837 each say the ticket's labels are correct, naming
`codebase-architecture` among them, while `triage-labels.md` had no row for it. A sweep comment on #897
treated the label as an expected slot. It called that ticket's `needs-triage` stale on the ground that
every other ticket in the sweep carried `codebase-architecture` in that position. *Corrected 2026-09-10:
this sentence first said the sweep flagged #897 for lacking the label, and the comment says no such
thing. Found by the session's own tracker sweep.* A check of
each ticket's labels passed at least five times over a label absent from the vocabulary. It compares a
ticket's labels to one another and to the rows that exist, so a label with no row does not appear in
anything it reads.

## Ruled 2026-09-10

### 1. The label stays and marks the architecture lineage

`codebase-architecture` remains a live label. It marks the **architecture lineage**, the term
`CONTEXT.md` defines: the tickets an architecture review placed, together with every ticket generated
by working one of them. It is a live lineage label, so new tickets keep receiving it for as long as the
lineage's members generate work. It is not retired as an episode tag in the way ADR 0072 ruling 4
retired `215 follow up`. Deletion was already ruled out by that ruling.

### 2. Membership is by descent only

A ticket carries the label when an architecture review placed it, or when it was generated by working a
ticket that carries it: the questions and measurements of that ticket's own grilling, what a build of
that ticket turns up, or a split or follow-up filed out of either. A build counts as working the ticket
for the same reason its grilling does: both are scoped to that one ticket. Closed #842, *"Found while
implementing #830"*, is the recorded instance, and the sixth question put this case to the clinician
because every earlier question had named only grilling. A ticket that looks like architecture work but descends from nothing a review
placed does not carry it, whatever its subject. A documentation ticket generated by working a member,
such as #1009, does carry it. #921 and #922 leave the lineage.

The purpose is following the work back to a review. A label anyone may add on judgment cannot be
followed, because it no longer tells a reader whether a ticket is in the lineage by ancestry or by
opinion.

### 3. A closing sweep's findings do not inherit

The whole-tracker sweep that closes a member's grilling is not work on that member. What it finds
carries the label only when the finding is about a lineage member. #1047 leaves the lineage.

Every grilling session ends with a sweep that reads every open ticket. If the label passed to
everything that sweep filed, each lineage grilling could pull in work from anywhere on the tracker, and
following the label would stop isolating what a review started.

### 4. The row is written in the orthogonal table, and the description moves with it

`triage-labels.md` gains a row for `codebase-architecture` in its *Orthogonal local labels* table,
stating the membership rule from rulings 2 and 3. The row also says who applies the label: the session
placing an architecture review's tickets, and a session filing a ticket generated by working a member,
at creation. It is orthogonal to the role labels and to `blocked`. The GitHub description string moves
with the row, as ADR 0072 ruling 1 moved `blocked`'s, so the two do not describe different rules.

### 5. The sweep compares the whole label vocabulary once

Once per sweep, the sweep compares `gh label list` against `triage-labels.md`, and a label the file does
not name is a finding. A label is named by a row in one of the file's tables or by the prose entry ADR
0072 ruling 4 gave it: `in flight` has a pointer to its home in `issue-tracker.md`, and GitHub's default
labels share one sentence. Demanding a table row for those would force the second copy that ruling
refused. *Corrected 2026-09-10, before the build started: this ruling and ruling 6 first said "a label
with no row", which read literally would have made `in flight` a finding on the first run. Two sweep
readers found it independently. The clinician's intent, an undocumented label, is unchanged.* This lands as prose in `docs/agents/issue-tracker.md` beside the `blocked` invariant. No
tool is built, on ADR 0072 ruling 3's reasoning: the tools open no sockets for this, and a grader would
need a new harvest step to certify what a sweep can check by reading two lists.

This is a comparison of the whole vocabulary, not the per-ticket audit sweeps already perform. The
measurement above is why a per-ticket audit cannot replace it.

### 6. Whoever creates a label adds its entry

A session that creates a label adds its entry to `triage-labels.md` in the same session: a table row,
unless the label's definition already has a home elsewhere and the entry is a pointer to it. The rule lands
in `issue-tracker.md`'s *Every issue you create gets a label* section as a pointer to
`triage-labels.md`, not a second copy of the vocabulary. Ruling 5 is what catches the case where this
rule is skipped, as it was on 2026-09-03.

### 7. Relabeling reaches open tickets only

Rulings 2 and 3 are applied to open tickets. Closed tickets keep the labels they closed with, in both
directions: a closed carrier outside the lineage keeps the label, and a closed descendant without it
stays unlabeled.

## Rejected options

- **Define the label by kind of work.** It would mark any ticket whose fix changes how code is
  organized, wherever the ticket came from. Refused because the label exists to follow a review's work,
  and a subject test cannot be followed.
- **Retire it as an episode tag.** Refused because its source keeps generating work: 14 open carriers,
  ten of them created on 2026-09-09 or 2026-09-10, and a tag nobody may apply would leave them marked with
  a closed episode.
- **Keep the literal GitHub description, found by an architecture review, and strip every descendant.**
  Refused because it drops the grillings' output from the lineage the clinician follows, for a
  distinction nobody used.
- **Let a closing sweep's findings inherit.** Refused under ruling 3.
- **A GitHub Actions check on the `label` created event.** It needs no network access from a tool, but
  the ordinary order of work creates a label while filing a ticket, before any row exists, so it would
  go red on the normal path and teach people to ignore it.
- **Relabel closed tickets.** Refused by the clinician: *"no need to fuck with old tickets."*

## Consequences

The build is the row, the description string, the two `issue-tracker.md` paragraphs, and the open
relabel. #1047's *Done when* is restated as predicates over `gh label list` and `gh issue list --state
open --label codebase-architecture` rather than an enumerated ticket list. The enumerated list went
stale twice on 2026-09-10 on ordinary tracker traffic, which ADR 0072's consequences section records as
the same shape for `blocked`.

## What this does not reach

- **Whether a closed ticket's label is right.** Ruling 7 leaves closed tickets alone, so a closed
  ticket's label is not evidence of lineage membership in either direction.
- **Whether a filer knows the ticket being worked is a member.** Descent is judged by the filing
  session at creation. Nothing checks it afterward except a sweep reading provenance lines.
- **A label created and deleted between two sweeps.** Ruling 5 compares the vocabulary at the moment
  a sweep runs.
- **The `/improve-codebase-architecture` skill itself.** It is a plugin skill outside this repository,
  and nothing here makes it apply the label. The rule reaches the session through `triage-labels.md`.
